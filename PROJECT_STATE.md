## IN-APP PASSWORD CHANGE (25 Jul 2026)

User asked for "a field to change password in superadmin and admin". Two surfaces, both live:

- **Self-service (`POST /auth/change-password`)** — requireAuth + authLimiter (takes a password guess as input) + `validateChangePassword` (currentPassword required, newPassword ≥ 8). `auth.service.changePassword` loads the live user with hash, verifies the CURRENT password (a live session alone isn't proof — unattended laptop), rejects same-as-old, hashes at cost 12, then **revokes every OTHER session** via `revokeOtherUserRefreshTokens(userId, currentSessionId)` so a stolen refresh token dies while this login survives. Endpoint is role-agnostic on purpose; the UI card (`features/settings/components/ChangePasswordCard.jsx`, current/new/confirm + inline errors) renders in My Profile **only for isAdminRole** per the user's request — employees/clients keep the forgot-password note (now hidden for admins).
- **Admin resets a managed user's password (Team → Edit)** — `EditUserModal` gained an optional "Set New Password" field (blank = unchanged; sent only when non-empty). Server: `user.service.updateUser` consumes `rawUpdates.password` explicitly OUTSIDE the UPDATABLE_FIELDS whitelist (the whitelist still blocks any direct `passwordHash` writes), gated by the existing `assertCanManage` (admin → own employees/clients; superadmin → anyone), hashes it, and **revokes ALL of the target's sessions** (they must log back in with the new password). `validateUpdateUser` enforces ≥ 8 chars when present.

## TWO-FACTOR AUTHENTICATION (21 Jul 2026)

Next roadmap item, picked autonomously — and a deliberate callback: when the login page was redesigned to match the user's reference image, I explicitly refused to copy its fake "1. Authenticate → 2. Verify" 2FA step indicator since it wasn't a real feature ("shipping dead UI that does nothing on click" was called out as against this project's own conventions). This round makes it real instead of leaving that as a permanent gap.

- **Library choice**: `otplib`'s latest major (v13) turned out to be a rewrite around async crypto plugins — its `generate()`/`verify()` return Promises and require plugin wiring that kept failing in quick testing. Downgraded to **`otplib@12.0.1`**, which exposes the classic synchronous `authenticator` object (`generateSecret()`, `generate(secret)`, `check(token, secret)`, `keyuri(email, issuer, secret)`) — the same API essentially every Node TOTP integration uses, zero plugin config. Paired with `qrcode` (`toDataURL`) to render the enrollment QR entirely server-side as a data URI — the client needed no new dependency at all, just an `<img src>`.
- **Model**: `User.twoFactor { enabled, secret, pendingSecret, backupCodeHashes[], confirmedAt }` — `secret`/`pendingSecret`/`backupCodeHashes` are all `select:false`, so a normal `findById` can never leak them; only `authRepository.findUserById(id, {with2FA:true})` pulls them in, and only the 2FA code paths ever call it that way. `pendingSecret` holds the freshly-generated secret between `/2fa/setup` and `/2fa/enable` — it only gets promoted to the real `secret` once the user proves they scanned it by submitting a valid code back.
- **New utility** `server/src/utils/twoFactor.js`: wraps otplib+qrcode, plus backup codes — 8 codes (`XXXXX-XXXXX` format) generated at enable time, shown to the user exactly once, only their bcrypt hashes ever persisted (same treatment as passwords). `matchBackupCode` returns the matching index so the caller can splice it out — each code is single-use.
- **Login flow**: `POST /auth/login` returns `{requires2FA:true, tempToken}` instead of a real session when `user.twoFactor.enabled` — `tempToken` is a `signPurposeToken(..., '2fa_login', '10m')` (reusing the existing purpose-token mechanism used for password-reset/email-verify links), never a real access token, redeemable only by the new `POST /auth/2fa/verify-login {tempToken, code}`, which accepts either a live TOTP code or an unused backup code and then issues a normal session exactly like `login()` does.
- **New role-vs-capability-style gate**: setup/enable/disable are self-service (`requireAuth`, act on `req.user.id`); `disable` re-verifies the account password before clearing `twoFactor` (standard practice — a stolen session alone shouldn't be able to turn off 2FA). `verify-login` is deliberately a **public** route (rate-limited via the existing `authLimiter`) since the caller has no session yet, only the tempToken.
- **Frontend**: `LoginPage.jsx` grows a second step (shown when `login()` resolves `{requires2FA}` instead of a user) — code input, "Back" to re-enter credentials, and a toggle to "Use a backup code instead" (same input, different placeholder/copy, backend tries TOTP first then falls back to backup-code matching either way so the toggle is purely a UX hint). New `AuthContext.verifyTwoFactor(tempToken, code)` mirrors `login()`'s session-setting logic. New Settings > My Profile card `TwoFactorSettings.jsx`: Enable → QR code + manual-entry secret + confirm-code form → one-time backup-codes reveal (copy-to-clipboard) with a "usual codes never shown again" warning → Disable → password-confirm modal. `User.toSafeJSON()` now exposes only a `twoFactorEnabled` boolean, never the secret/codes.
- **Verified end-to-end via curl** (computing real TOTP codes against the returned secret with a one-off `otplib` script): no-2FA login unaffected; setup returns a secret + valid QR data URL; enable rejects a wrong code (400) and accepts the real code (200, 8 backup codes returned); a subsequent login now returns `requires2FA` with no access token; verify-login rejects a wrong code (401), accepts the real TOTP code (200 + session), accepts a backup code (200 + session), and **rejects that same backup code on reuse** (401 — single-use confirmed); disable rejects the wrong password (401) and accepts the correct one (200); login after disabling no longer requires 2FA. Browser: full enrollment through the Settings UI (QR + manual secret rendered, wrong code rejected inline, real code accepted, 8 backup codes displayed), logout, login again correctly shows the code-entry step (wrong code rejected with a toast, real code logs in and lands on the Service Launcher), then disabled again via the UI's password-confirm modal to leave the test account clean. (Mid-verification the sandbox's system clock jumped forward ~2 days between tool calls, which briefly desynced a pre-computed TOTP code and expired a tempToken — an environment artifact, not a code bug; regenerating the code and re-logging-in against the now-stable clock immediately worked, confirmed by comparing the DB-stored secret against the displayed one.) Client build clean, all 13 server tests pass.

## STACK PIVOT (post-Phase-1, locked — supersedes anything in ARCHITECTURE.md that conflicts)

User rejected the TypeScript/Redux Toolkit/TanStack Query/Radix-Shadcn/Framer Motion/socket.io/recharts version mid-Phase-2. Corrected stack:

- **Plain JavaScript everywhere.** No TypeScript, no `.ts`/`.tsx`, no type-checking build step. `server` uses CommonJS (`require`/`module.exports`). `client` uses ESM (`import`/`export`) via Vite's default JS/JSX handling.
- **No Redux, no Redux Persist, no TanStack Query/Table.** Client/server-ish caching state is plain `useState`/`useEffect`/`useContext`. Auth session lives in `AuthContext` (`client/src/features/auth/context/AuthContext.jsx`), persisted to `localStorage` manually.
- **No Radix/Shadcn/Tailwind.** Hand-rolled components in `client/src/components/ui/` and `components/shared/`, styled with plain CSS files (one stylesheet per component, colocated) using the CSS custom properties defined in `client/src/index.css`.
- **No Framer Motion.** CSS transitions only.
- **No socket.io.** Real-time notifications dropped for v1; notification bell polls on an interval. `server/src/sockets/` and the "Real-Time" section of `docs/ARCHITECTURE.md` §7 are superseded — no socket layer exists.
- **No recharts/chart libs.** Dashboard charts are hand-rolled inline SVG components in `client/src/features/dashboard/components/`.
- **No date-fns.** Native `Intl.DateTimeFormat` / `Date` only.
- **No Zod on either side.** Validation is plain hand-written validator functions (`server/src/features/<mod>/validators/*.validator.js`, return `{ isValid, errors }`), plus native HTML5 + manual JS validation on forms client-side.
- **Roles simplified to two:** `admin` and `user` (not the original 7-role list). Still implemented capability-based (`can(user, 'client:delete')` resolving through a `roleCapabilities` map in `server/src/middlewares/rbac.middleware.js`) so a future role can be added without touching route code — user said they'll define what `admin` vs `user` can do later; for now `admin` = full capability set, `user` = read + create/update own records, no delete, no settings/user-management access. Revisit when user specifies.

## Conventions Locked In

- Monorepo, two npm workspaces: `server/` (Express, plain JS) and `client/` (React 19 + Vite, plain JS/JSX).
- Max ~250 lines per file; split by sub-concern when exceeded.
- Backend layering strict: `routes → controller → service → repository → model`. Controllers never call Mongoose directly.
- All API responses use the shared envelope from `server/src/utils/ApiResponse.js`: `{ success, message, data, meta?, error? }`.
- All list endpoints support `page, limit, sort, search, <field filters>` via shared `parseQuery` middleware + repository `paginate()` helper (Phase 4).
- Soft delete via `isDeleted` + `deletedAt` on every collection; no hard deletes from the API.
- Every collection carries `firmId`; repository base class scopes queries to it automatically.

## Frontend Complete (Phases 5-8) — Patterns to Follow If Extending

- **List pages**: `useApiData(() => xApi.list({ page, limit, search }), [page, search])` feeding a `<DataTable>` (`client/src/components/ui/DataTable.jsx`). Search/sort/pagination are server-side via the shared `parseQuery` contract — the table itself has no client-side data logic.
- **Create/edit**: a `<Modal>` + local `useState` form, no React Hook Form/Zod (hand-validated, see stack pivot). One `<ModuleFormModal>` component per feature under `features/<mod>/components/`.
- **Client picker pattern** (used in Invoice/Receipt/Ledger forms): `useApiData(() => clientApi.list({ limit: 100, status: 'active' }))` fed into a `<Select>`. Fine at current scale; would need a real async-search combobox if a firm has hundreds of clients — not built.
- **CSV export**: `downloadCsv()` in `features/reports/services/report.service.js` — fetches as a blob via `apiClient` (so the auth header attaches) rather than a plain `<a href>`, since the API requires a Bearer token.
- **Print views** (ledger statement, invoice): a `.no-print` CSS class + `window.print()`, no PDF library. See `@media print` block in `client/src/index.css`.
- **Self-service profile fix**: `PATCH /users/:id` is admin-only (`user:update` capability, which the `user` role does NOT have per the RBAC split). A regular user editing their own name/phone goes through `PATCH /auth/me` instead (`authController.updateMe`, no capability gate beyond `requireAuth`) — added after noticing the gap while building `ProfileSettingsPage.jsx`. If you add more self-editable fields, extend `updateMe`/`validateUpdateMe`, not the admin user routes.
- **Documents page scope cut**: `DocumentsPage.jsx` uploads with `ownerType: 'firm', ownerId: user.firmId` — a firm-wide library only. Per-client/per-task document attachment (uploading directly from `ClientDetailPage`/`TaskDetailPage`) is not wired on the frontend yet, though the backend (`ownerType: 'client' | 'task'`) already supports it.

## Manual Verification Findings (real bug caught + fixed)

Ran both dev servers against a throwaway in-memory MongoDB and drove the app through the browser (login → create client → client detail/timeline → khata book entry → invoice creation). Found and fixed one real bug in the process:

- **`useApiData`'s `skip` option was stale-closured** (`client/src/hooks/useApiData.js`): the `skip` check lived inside the `useCallback`-memoized `load` function, gated only by the `deps` array — so a `skip: true → false` transition (e.g. `ClientDetailPage`'s timeline fetch, gated on the parent client record loading first) never re-triggered a fetch. Confirmed live in the browser: the client timeline stayed empty despite an activity log entry existing server-side. **Fixed** by moving the `skip` check out of `load` and into the `useEffect` that calls it, with `skip` added to that effect's own dependency array, so it's always read fresh. This affects every consumer using `{ skip }` — `ClientDetailPage` timeline, `InvoiceFormModal`/`StandaloneReceiptModal` client-picker dropdowns, `RemindersPage` calendar tab, `ReportsPage` tabs — all re-verified working after the fix.
- Everything else exercised (auth/session-refresh across tabs, client CRUD, ledger running-balance math, invoice line-item tax calculation, invoice numbering) worked correctly on the first pass.
